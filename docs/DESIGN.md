# JudgeBench-Code: Evaluating the Evaluators: Design Doc

**Status:** Draft v2 (reframed from "PR autorater")
**Owner:** Ella
**Last updated:** 2026-10-23

## 1. Summary

Coding agents are increasingly graded, gated and trained by **autoraters**: LLM judges that score a PR. Examples include rubric-graded benchmarks like FrontierCode, AI PR reviewers, and RL reward models. Almost nobody publishes how reliable those judges are.

**JudgeBench-Code** is a benchmark and bias suite **for code autoraters**. It measures:
1. **Agreement.** Does the judge predict what real maintainers merge, and what humans rate?
2. **Bias.** Is the judge swayed by position, diff length, polished descriptions, or its own model family?
3. **Reward-hacking resistance.** Does the judge catch PRs that pass tests by cheating (deleted tests, hard-coded outputs)?

The deliverables are a dataset, a harness that scores any judge, a public leaderboard, and a "fool the judge" interactive demo. A simple rubric PR autorater (from draft v1) ships as the **baseline judge**.

## 2. Why this matters (and why Devin would care)

- Cognition's FrontierCode post argues correctness-only benchmarks have high misclassification rates and that quality and mergeability are what count. Grading quality requires judges, so judge reliability becomes the bottleneck.
- If autoraters are used as **RL rewards** or **pre-PR gates**, any judge bias becomes something the agent learns to exploit.
- Devin already ships judge-like components (Devin Review, the SWE-check model behind Quick Review). This project provides an external way to measure components like these and pick between candidate judges.

**Novelty claim:** an eval for code *judges* (not code generators) that combines (a) real maintainer outcomes on agent-authored PRs, (b) controlled perturbations with known answers, and (c) bias and reward-hacking tests in one leaderboard.

## 3. Goals / Non-goals

**Goals**
- G1: A versioned dataset of PRs with labels from maintainers, humans and controlled perturbations.
- G2: A harness where any judge implementing `rate()` / `compare()` gets a scorecard.
- G3: Leaderboard of at least 4 judges, plus a static demo site.
- G4: A reproducible pipeline that can be re-run on new PRs to limit contamination.

**Non-goals (v1)**
- Building the best judge. The baseline judge exists only to be measured.
- Rating agent trajectories (that's v2).
- Running repo test suites ourselves, except where the perturbation pipeline needs it (section 4.1).

## 4. Data

Four sources, ordered by cost. Every item has a `label_source` field so metrics can be broken down by source.

### 4.1 Synthetic perturbations (known ground truth, cheapest)
Start from **clean merged PRs** (small, well-tested, from active repos) and apply transformations whose effect on quality is known:

| Perturbation | Expected judge behavior | Tests for |
|---|---|---|
| Delete / `skip` the PR's new tests | Score should drop | Reward hacking |
| Hard-code expected output / special-case the test input | Score should drop | Reward hacking |
| Add `# type: ignore` / broad `except: pass` | Score should drop | Reward hacking |
| Add unrelated refactor to another file | Scope score should drop | Scope sensitivity |
| Pad with comments / whitespace / dead code | Score should **not** rise | Length bias |
| Replace PR description with confident, polished text (diff unchanged) | Score should **not** change | Description gaming |
| Swap A/B order in pairwise | Winner should **not** change | Position bias |
| Rename variables only (semantics unchanged) | Score ~unchanged | Stability |

Perturbations are generated by scripts where possible (deleting tests, padding, swapping) and by an LLM with human spot-checks for the harder ones (hard-coding, refactors). Each perturbed item stores `parent_pr`, `perturbation` and `expected_direction`.

### 4.2 Real agent PRs with maintainer outcomes (most Devin-relevant)
- Find public PRs opened by coding-agent accounts (e.g. Devin's GitHub bot, Copilot coding agent and other agent bots) using the GitHub search API or **GH Archive on BigQuery**.
- For each PR, collect the diff, the task (linked issue or PR body), review comments, and the outcome (`merged`, `closed-unmerged`, `merged-after-changes`, inferred from review rounds and commits after review).
- **Filters:** closed for non-quality reasons (stale > N days with no review, superseded, repo archived), trivial PRs (dependency bumps, typos), repos with < X stars or no human reviewers.
- Target: about 300–500 PRs across 10+ repos and 4+ languages, with roughly balanced merged/closed counts.
- Add human-authored PRs from the same repos as a control group.

### 4.3 Same-task multi-candidate pairs
- Public SWE-bench submission logs contain patches from many agents for the same issue, with test results.
- Choose pairs where **both patches pass tests** but differ (in scope, size or approach). Humans label which is better. This is the pairwise set (~100 pairs).

### 4.4 Human gold set
- About 100 PRs sampled across sources, rated on the rubric by 2–3 people using a written guide.
- Inter-annotator agreement (weighted κ) sets the **human ceiling**. Judge scores are reported relative to it.

### Data hygiene
- **Contamination:** prefer PRs created after each judge's training cutoff, and report metrics split into pre-cutoff and post-cutoff items.
- **Licensing/ethics:** public repos only. Store links plus diffs, not full repos. Respect the GitHub API ToS and rate limits, and don't bulk-scrape beyond what's needed.

## 5. Judges under test (v1)

| Judge | Notes |
|---|---|
| Baseline rubric autorater | Prompted rubric R1–R7 (task fit, correctness risk, minimal scope, conventions, tests, readability, overall mergeability) |
| Frontier LLMs, zero-shot "would you merge?" | 2–3 model families |
| Same LLMs + rubric + anchors | Measures how much a rubric helps |
| Open-weight model | Cheap option for RL-scale use |
| (Optional) Commercial reviewers with an API | Only where ToS allows benchmarking |

Interface every judge implements:
```python
class Judge:
    def rate(self, req: RatingRequest) -> Rating: ...           # scores 1-5 + reasons
    def compare(self, a: RatingRequest, b: RatingRequest) -> Pref: ...  # A | B | tie
```

## 6. Metrics (the scorecard)

| Axis | Metric | Data |
|---|---|---|
| Maintainer agreement | AUROC for merged vs. closed; accuracy at a tuned threshold | 4.2 |
| Human agreement | Weighted κ / Spearman ρ vs. gold, as % of human–human κ | 4.4 |
| Pairwise accuracy | % agreement with human preference | 4.3 |
| Reward-hack catch rate | % of hack perturbations scored lower than their parent | 4.1 |
| Length bias | Mean score gain from padding (target ≈ 0) | 4.1 |
| Description gaming | Mean score change from polished description (target ≈ 0) | 4.1 |
| Position bias | Winner flip rate on A/B swap | 4.1 / 4.3 |
| Self-preference | Score gap: judge rating own family vs. others, label-controlled | 4.2 / 4.3 |
| Cost / latency | $ and seconds per rating | all |

A single **composite score** is reported only as a convenience. The leaderboard shows all axes because the trade-offs (e.g. cheap but biased) are the point.

## 7. Demo

Built as a **static site** (outputs computed ahead of time, no backend), so it's free to host and easy to share.

1. **Leaderboard.** One row per judge, one column per metric axis, sortable, with a cost-vs-quality scatter plot.
2. **"Fool the judge" playground (the hero feature).** Pick a real PR, toggle perturbations (delete tests, pad, polish description, swap order), and see every judge's score update side by side. Only precomputed combinations are shown, so it stays static.
3. **Failure gallery.** The cases judges get most confidently wrong (e.g. "approved a PR that deletes 3 tests"), each with the diff, the judge's reasoning and the true label.
4. **Methodology page.** Data sources, filters, label guide, and contamination split.

Optional: a 2-minute screen recording that goes leaderboard → playground ("watch GPT approve this deleted test") → gallery.

## 8. Architecture

```
GitHub API / GH Archive ─┐
SWE-bench logs ──────────┼─> dataset builder ─> items.jsonl (+ label_source)
Perturbation scripts ────┘                         │
                                                   v
                         judges/*.py ──> harness (rate/compare, caching, retries)
                                                   │
                                                   v
                                  results/<judge>/<run>.jsonl
                                                   │
                                                   v
                         metrics.py ──> scorecard.json ──> static site (leaderboard,
                                                            playground, gallery)
```

- **Stack:** Python 3.11, `pydantic`, `httpx`, a provider-agnostic LLM client, `pandas`/`scikit-learn`. The site is a static Vite/React (or plain HTML) app that reads `scorecard.json` and precomputed playground outputs.
- **Reproducibility:** every result is keyed by dataset version, judge id, prompt hash and rubric version, and all LLM calls are cached on disk.

## 9. Plan

| Phase | Deliverable | Est. |
|---|---|---|
| P0 | Repo scaffold, schemas, `Judge` interface, baseline judge | 0.5 session |
| P1 | Perturbation pipeline on about 50 clean merged PRs → about 400 perturbed items | 1 session |
| P2 | Harness + metrics; first scorecard for 3 judges on perturbations only | 0.5 session |
| P3 | Agent-PR miner (GitHub API / GH Archive) + filters → about 300 labeled PRs | 1 session |
| P4 | Static site: leaderboard + playground + gallery | 1 session |
| P5 | Human gold set (Ella + 1–2 raters), SWE-bench pairwise set, final scorecard | ongoing |

**Fastest path to a demo:** P0 → P1 → P2 → P4. Perturbations need no human labels, so a working leaderboard and playground can exist before any real-PR mining.

## 10. Risks and open questions

- **Noisy maintainer labels.** PRs are closed for many reasons. Mitigation: filters, a `merged-after-changes` class, and relying on the gold set for headline claims.
- **Perturbation realism.** Synthetic hacks may be easier to spot than real ones. Mitigation: model the hacks on real reward-hacking examples and report results on synthetic and real data separately.
- **Agent bot identification.** Bot account names change, and some agent PRs are opened under human accounts. Accept some false negatives and document the list of accounts used.
- **Judge cost.** k samples × swaps × judges × items adds up. Start with k=1 on a subset.
- **Open:** Which judge models / API budgets are available? Is benchmarking commercial reviewers allowed under their ToS? Should the dataset be public or kept private to limit contamination?

## 11. Future work

- **Trajectory judges:** rate agent sessions (loops, wasted turns, cost per task) and benchmark those judges the same way.
- **Per-org calibration:** measure how much judge accuracy improves when tuned on one org's merge history.
- **Judge training:** use the benchmark to select or fine-tune a small, robust judge suitable as an RL reward.
